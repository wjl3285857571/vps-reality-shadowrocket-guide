# 03｜安全、验收与回滚

## 1. 分层验收模型

不要把不同阶段混为“已经搭好”。建议分成六层：

| 层级 | 要回答的问题 | 推荐证据 |
|---|---|---|
| 已安装 | Xray 程序是否存在？ | `xray version` |
| 配置有效 | JSON 与字段是否被当前版本接受？ | `xray run -test` |
| 正在运行 | systemd 服务是否存活？ | `systemctl is-active xray` |
| 正在监听 | 目标端口是否属于 Xray？ | `ss -lntp` |
| 外部可达 | VPS 外部能否连接端口？ | 外部 TCP 测试 |
| 真实可用 | 客户端能否完成请求并得到 VPS 出口？ | 客户端代理实测 |

任何一层失败，都不能用下一层的“看起来正常”替代。

## 2. 服务端验收

运行仓库脚本：

```bash
sudo LISTEN_PORT=443 bash scripts/verify-server.sh
```

或手动执行：

```bash
sudo /usr/local/bin/xray run -test \
  -config /usr/local/etc/xray/config.json
sudo systemctl is-active xray
sudo ss -lntp | grep ':443'
sudo journalctl -u xray -n 100 --no-pager
```

日志中不要输出完整配置或客户端参数。

## 3. 外部验收

从另一台机器测试 TCP：

```bash
nc -vz <VPS_IP> 443
```

TCP 成功只证明端口可达，不证明 REALITY 参数正确。完整验证需要使用真实客户端配置发起请求，但测试配置必须放在临时目录并设置 `600` 权限，测试结束后删除。

## 4. 客户端验收

依次检查：

1. Shadowrocket 开关保持开启；
2. 当前节点正确；
3. 内置连通性测试通过；
4. 普通 HTTPS 页面可打开；
5. IPv4 出口符合预期；
6. IPv6 出口符合预期或未启用；
7. DNS 不出现本地运营商；
8. WebRTC 不暴露本地公网地址；
9. 定位数据库没有明显冲突；
10. 常用业务网站连续使用正常。

风险评分是辅助信号，不是绝对结论。不同数据库的评分口径、更新时间和地理标注可能不同。

## 5. Xray 回滚

如果新配置导致服务异常：

```bash
sudo cp -a <BACKUP_CONFIG> /usr/local/etc/xray/config.json
sudo /usr/local/bin/xray run -test \
  -config /usr/local/etc/xray/config.json
sudo systemctl restart xray
sudo systemctl is-active xray
```

不要在未通过 `run -test` 时重启。

## 6. UFW 回滚

如果启用 UFW 后 SSH 出现风险，保持当前会话，不要退出。先检查：

```bash
sudo ufw status numbered
sudo ss -lntp | grep ':<SSH_PORT>'
```

必要时通过 VPS 控制台执行：

```bash
sudo ufw disable
```

然后修正规则，重新验证后再启用。

## 7. Fail2ban 回滚

如果自己的地址被封禁，优先使用 VPS 控制台：

```bash
sudo fail2ban-client status sshd
sudo fail2ban-client set sshd unbanip <YOUR_ADMIN_IP>
```

不要把管理地址写入公开文档或仓库。

## 8. Shadowrocket DNS 回滚

按照修改顺序逆序恢复：

1. 先把备用 DNS 恢复为修改前的值；
2. 保存并复测；
3. 再把主 DNS 恢复为修改前的值；
4. 保存并复测；
5. 如果配置损坏，再恢复完整备份。

不要同时恢复 DNS、IPv6、路由和规则，否则无法判断哪个变化解决了问题。

## 9. 绝不能上传的文件

包括但不限于：

```text
真实客户端参数文件
节点 URI
二维码
Shadowrocket 容器备份
Xray 服务端配置
Reality 私钥、公钥/Password、Short ID
UUID
SSH 私钥、公钥清单和 authorized_keys
VPS 地址、域名或供应商管理资料
日志中的公网地址、Token、Cookie、Session
```

即使仓库是私有的，也应按“未来可能误设为公开”来处理。

## 10. 提交前检查

先执行：

```bash
bash scripts/check-sensitive.sh
git status --short
git diff --cached
```

确认暂存区只包含通用文档和脚本。不要使用不加检查的 `git add -A`。

## 11. 凭据疑似泄露后的处理

如果任何真实节点材料进入 Git 历史：

1. 立即停止继续推送；
2. 轮换 UUID、REALITY 密钥和 Short ID；
3. 删除或替换受影响客户端配置；
4. 清理 Git 历史，而不是只删除最新文件；
5. 检查 GitHub Actions、日志、PR 和缓存；
6. 重新运行敏感信息扫描；
7. 把旧凭据视为永久失效。
